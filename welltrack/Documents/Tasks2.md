# WellTrack — Implementation Tasks (v2)

An independent task breakdown of [Documents/Requirements.md](Documents/Requirements.md), grouped by the
12-week timeline. **Requirements.md is the source of truth** for exact field lists, value ranges, and
endpoint contracts — these tasks reference them rather than repeating them, so check there when a
detail is unclear.

Each checkbox is meant to be one sittable unit of work for a mid-level developer. Tasks within a
section are roughly in dependency order; sections themselves can often run in parallel once the
schema and auth middleware exist.

---

### 1.1 Project setup

- [x] Create the repo structure: `server/` and `client/` as separate packages (keeps deploy targets independent)
- [x] Init `server/` as Node.js + Express with TypeScript; add `tsx`/`ts-node-dev` for hot reload
- [x] Add ESLint + Prettier with a shared config, and a `npm run lint` script that CI can call
- [x] Add a `docker-compose.yml` with a PostgreSQL service so every dev gets the same local database
- [x] Install and init Prisma; point `DATABASE_URL` at the local PostgreSQL instance
- [x] Create `.env.example` listing every required variable: `DATABASE_URL`, `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, token TTLs, SMTP/email provider keys, `CLIENT_URL`
- [x] Add a config module that reads `process.env` once at boot and throws on missing required vars (fail fast, not at first request)
- [x] Set up the folder layout: `routes/`, `controllers/`, `services/`, `middleware/`, `validators/`, `prisma/`
- [x] Add a `GET /api/health` endpoint returning `200` plus a database connectivity check

### 1.2 Database schema

Model each of these in `prisma/schema.prisma` using the field lists in Requirements.md → Data Model.
All ids are UUIDs generated by the database.

- [x] `User` — email is unique, `timezone` defaults to `"UTC"`
- [x] `Symptom` — `user_id` is nullable; a null `user_id` means it is a system default shared by all users
- [x] `SymptomLog` — `severity` is an integer 1-10
- [x] `MoodLog` — `mood_score` 1-5 required; `energy_level` and `stress_level` 1-5 optional
- [x] `Medication` and `MedicationLog`
- [x] `Habit` — `tracking_type` as an enum of `boolean` / `numeric` / `duration`
- [x] `HabitLog` — three nullable value columns, one per tracking type; `value_duration` is stored in minutes
- [x] Add `onDelete: Cascade` on every user relation so `DELETE /api/users/me` removes all data in one transaction
- [x] Add a composite index on `(user_id, logged_at)` for `SymptomLog`, `MoodLog`, and `HabitLog`, and on `(user_id, created_at)` for `MedicationLog`
- [x] Add an index on `(user_id, is_active)` for `Symptom`, `Habit`, and `Medication` — the picker lists filter on both
- [x] Add a `RefreshToken` model (token hash, user_id, expires_at, revoked_at) — needed for logout and rotation to actually work
- [x] Add a `PasswordResetToken` model (token hash, user_id, expires_at, used_at)
- [ ] Run the initial migration and commit the generated migration files
- [x] Write the seed script for the 11 default symptoms listed in Requirements.md, each with `user_id = null` and a sensible `category`
- [x] Write the seed script for the 5 default habits listed in Requirements.md, each with `user_id = null` and its correct `tracking_type` and `unit`
- [x] Make the seed script idempotent (upsert by name) so it is safe to re-run against an existing database
- [ ] **Manual follow-up:** no Postgres was reachable in the dev environment this was built in (no Docker installed, nothing listening on `localhost:5432`). Schema, migration tooling config, and `prisma/seed.ts` are written and type-check cleanly against the generated client, but the migration has never actually been applied or run against a real database. Once Postgres is available: `docker compose up -d`, then from `server/` run `npx prisma migrate dev --name init` (commit the generated `prisma/migrations/` folder), then `npm run db:seed` twice to confirm it's idempotent, then spot-check the 11 symptoms / 5 habits and table shapes.

### 1.3 Authentication

- [x] Hash passwords with bcrypt (cost factor 12) in a `passwordService`; never let a raw password reach the controller layer
- [x] `POST /api/auth/register` — validate email format and password strength, reject duplicate emails with `409`, return tokens on success
- [x] Write the token service: sign short-lived access JWTs (~15 min) and long-lived refresh tokens (~30 days), storing only a hash of the refresh token in the database
- [x] `POST /api/auth/login` — verify credentials, issue both tokens; return the same generic error for unknown email and wrong password so the endpoint does not leak which accounts exist
- [x] `POST /api/auth/refresh` — validate the refresh token, revoke it, and issue a fresh pair (rotation); reject reuse of an already-revoked token
- [x] `POST /api/auth/logout` — revoke the presented refresh token
- [x] `POST /api/auth/forgot-password` — create a single-use reset token, email a link to `CLIENT_URL/reset-password?token=...`; always return `200` even for unknown emails
- [x] `POST /api/auth/reset-password` — validate the token is unused and unexpired, update the password hash, revoke all of that user's refresh tokens
- [x] Wire up an email sender (start with a dev console transport, swap to a real provider before deploy)
- [x] Write `requireAuth` middleware that verifies the access JWT and attaches `userId` to the request
- [x] Add rate limiting to `/api/auth/login`, `/api/auth/register`, and `/api/auth/forgot-password` to blunt brute-force and email-flood attempts

### 1.4 User endpoints

- [ ] `GET /api/users/me` — return the profile without `password_hash`
- [ ] `PATCH /api/users/me` — update `display_name` and `timezone`; validate the timezone is a real IANA zone name
- [ ] `DELETE /api/users/me` — delete the user and let the cascade remove all logs, custom symptoms, habits, and medications

### 1.5 Symptoms and symptom logs

- [ ] `GET /api/symptoms` — return system defaults plus the user's own custom symptoms, excluding rows the user has hidden — *implemented without the hide-exclusion: returns system defaults + the caller's own symptoms; nothing sets a row hidden yet (see below)*
- [x] `POST /api/symptoms` — create a custom symptom owned by the caller
- [ ] `PATCH /api/symptoms/:id` — rename or toggle `is_active` on an owned symptom
- [ ] Decide and implement how a user hides a *system* symptom — a system row is shared, so hiding needs a per-user record (a `UserSymptomPreference` table or a hidden-ids list on the user) rather than flipping the shared row's `is_active`
- [ ] `DELETE /api/symptoms/:id` — allow only for user-owned symptoms; return `403` for system rows
- [x] `GET /api/symptom-logs` — support `startDate`, `endDate`, `limit`, `offset`; default to a sane page size and return a total count for the UI
- [x] `POST /api/symptom-logs` — validate `severity` is 1-10 and that `symptom_id` refers to a symptom the caller can see
- [x] `PATCH /api/symptom-logs/:id` and `DELETE /api/symptom-logs/:id`

### 1.6 Mood logs

- [x] `GET /api/mood-logs` with `startDate` / `endDate`
- [x] `POST /api/mood-logs` — validate `mood_score` 1-5, and `energy_level` / `stress_level` 1-5 when present
- [x] `PATCH /api/mood-logs/:id` and `DELETE /api/mood-logs/:id`

### 1.7 Medications and medication logs

- [x] `GET /api/medications` — the caller's medications; medications have no system defaults
- [x] `POST /api/medications` — `name` required, `dosage` and `frequency` optional free text
- [ ] `PATCH /api/medications/:id` and `DELETE /api/medications/:id`
- [ ] Decide what deleting a medication does to its existing logs — prefer soft-delete via `is_active` so historical logs stay intact
- [x] `GET /api/medication-logs` with `startDate` / `endDate`
- [x] `POST /api/medication-logs`, `PATCH /api/medication-logs/:id`, `DELETE /api/medication-logs/:id`

### 1.8 Habits and habit logs

- [x] `GET /api/habits` — system defaults plus the user's custom habits, honouring hidden rows the same way symptoms do — *implemented without the hide-exclusion: returns system defaults + the caller's own habits; nothing sets a row hidden yet (see below)*
- [x] `POST /api/habits` — create a custom habit with `tracking_type` and optional `unit`
- [ ] `PATCH /api/habits/:id` and `DELETE /api/habits/:id` (user-owned only)
- [ ] Decide and implement how a user hides a *system* habit — same open item as the symptom hide-preference mechanism
- [x] `GET /api/habit-logs` with `startDate` / `endDate`
- [x] `POST /api/habit-logs` — look up the parent habit and validate that the matching value field is set: `value_boolean` for boolean habits, `value_numeric` for numeric, `value_duration` for duration; reject requests that set the wrong one
- [x] `PATCH /api/habit-logs/:id` and `DELETE /api/habit-logs/:id`

### 1.9 Validation, errors, and ownership

- [ ] Add Zod schemas for every POST/PATCH body and every query string, applied by a shared `validate(schema)` middleware
- [x] Write centralized error-handling middleware that maps thrown errors to a consistent JSON shape (`{ error: { code, message, details } }`) and logs the stack server-side without leaking it to the client
- [x] Add an ownership guard used by every `:id` route: load the row, compare its `user_id` to the authenticated user, return `404` (not `403`) on mismatch so the API does not confirm the existence of other users' records
- [ ] Standardize date handling — accept and return ISO 8601 with offsets, store as `timestamptz`, and never assume the server's local zone

### 1.10 Backend testing

- [ ] Set up the test runner (Vitest or Jest) with a separate test database and a per-test reset — *Vitest itself is set up and is the runner for every test in this project; the "separate test database" half is not done. Same blocker as task 1.2: no Postgres is reachable in this dev environment (no Docker installed, nothing listening on `localhost:5432`), so there is nothing to point a test `DATABASE_URL` at or migrate. All tests in this suite instead run the real service/controller/route/middleware code against an in-memory fake Prisma client (see `src/test/fakeModelStore.ts` and the hand-rolled fake in `src/routes/authFlow.integration.test.ts`), which gives per-test isolation "for free" without a real database. Once Postgres is available and the task 1.2 migration has been run, this bullet should be revisited: point `DATABASE_URL` at a dedicated `welltrack_test` database and add a reset (e.g. truncate-all-tables) between tests.*
- [x] Unit-test the token service, password service, and habit-log value validation
- [x] Integration-test the auth flow end to end: register → login → refresh → logout → refresh fails
- [x] Integration-test one full CRUD cycle per log type, including a cross-user access attempt that must fail

## Phase 2: Frontend Foundation (Weeks 4-6)

### 2.1 App scaffold

- [x] Init `client/` with Vite + React + TypeScript
- [x] Install and configure Tailwind CSS
- [x] Define the theme: soft teal and sage as the primary palette, generous spacing, rounded corners — deliberately not a clinical blue/white medical look (see Requirements.md → Notes)
- [x] Set the base typography scale one step larger than default; the target users have fatigue and brain fog, so readability wins over density
- [x] Set up React Router with a public route group (login, register, forgot/reset password) and a protected group (everything else) — *route groups are wired with placeholder pages; the actual ProtectedRoute auth check is task 2.2*
- [x] Build the API client wrapper: base URL from env, `Authorization` header injection, JSON parsing, and typed error surfacing
- [x] Add a data-fetching layer (TanStack Query recommended) so caching and refetch-after-mutation are handled once rather than per screen
- [x] Generate or hand-write shared TypeScript types for API request/response shapes so client and server cannot drift silently

### 2.2 Auth UI

- [x] Register page with inline field validation and a clear duplicate-email error
- [x] Login page
- [x] Forgot-password page and reset-password page (reads the token from the query string)
- [x] Auth context/store holding the current user and access token
- [x] Store the refresh token and implement silent refresh: on a `401`, refresh once and retry the original request; on failure, clear state and redirect to login
- [x] `ProtectedRoute` wrapper that redirects unauthenticated users to login and preserves the intended destination
- [x] Logout action that calls `POST /api/auth/logout` and clears all local auth state
- [x] **Unplanned fix:** the server had no CORS middleware, so every cross-origin request from the Vite dev client (`localhost:5173`) to the API (`localhost:3000`) failed with `net::ERR_FAILED` in a real browser — found while manually driving this feature end to end. Added `cors` scoped to `config.CLIENT_URL` in `server/src/app.ts`.

### 2.3 Dashboard

- [x] Dashboard shell showing today's date rendered in the user's stored timezone
- [x] "Logged today" summary grouped by type, with an inviting empty state when nothing is logged yet
- [x] Quick-add buttons for symptom, mood, medication, and habit — the primary action on the screen, large and reachable with one thumb — *not yet wired to an action; they'll open the log-entry modal built in task 2.4*
- [x] "Days logged this week" indicator computed from the current week's logs
- [x] Loading skeletons and an error state for the dashboard's data fetch
- [x] **Bug found and fixed while manually driving the page:** `useDashboardData`'s query keys were built from a fresh `new Date()` computed on every render, so TanStack Query never saw a stable key and refetched in a tight loop, hammering the four log endpoints continuously. Fixed by computing `now`/`startDate`/`endDate` once per mount via `useMemo`.

### 2.4 Logging UI

- [ ] Build the shared log-entry modal: type selector, body slot, optional notes field, date/time picker defaulting to now, and a single prominent Save button
- [ ] Symptom form — searchable symptom picker plus a 1-10 severity control using large tap targets, not a thin slider
- [ ] Mood form — 1-5 mood selector, with optional energy and stress rows that stay collapsed until tapped
- [ ] Medication form — medication picker, taken/not-taken toggle, optional `taken_at` time
- [ ] Habit form — renders a checkbox, a number input, or a duration input based on the selected habit's `tracking_type`, and shows the habit's `unit` as the input label
- [ ] Backfill support — let the date/time picker move to any past date, and make backfilled entries visibly distinct from today's
- [ ] Wire every form to its endpoint, invalidate the relevant queries on success, and keep the form open with an error message on failure so no input is lost
- [ ] Accessibility pass on the modal: focus trap, Escape closes, all controls keyboard reachable, labels tied to inputs

## Phase 3: Full Features (Weeks 7-9)

### 3.1 History

- [ ] History page listing entries grouped by day, newest first
- [ ] Infinite scroll or paging driven by the `limit` / `offset` parameters the log endpoints already support
- [ ] Expand an entry to edit it inline, reusing the Phase 2 form components rather than duplicating them
- [ ] Delete an entry with a confirmation step
- [ ] Filter control for type (symptoms / mood / medications / habits), with the active filter reflected in the URL so it survives a refresh
- [ ] Empty state for both "no logs at all" and "no logs matching this filter"

### 3.2 Trends

- [ ] `GET /api/insights/trends?type=&days=` — aggregate the requested log type over the window, bucketed by day, returning a dense series that includes days with no data
- [ ] Do the day bucketing in the user's timezone, not UTC, or entries near midnight will land on the wrong day
- [ ] Add a charting library (Recharts is a reasonable default) and a shared chart wrapper carrying the app's palette
- [ ] Trends page with a 7 / 30 / 90 day range picker
- [ ] Symptom severity line chart with a selector for which symptom(s) to plot
- [ ] Mood / energy / stress line chart
- [ ] Calendar heatmap colour-coded by how much was logged each day, with the same range picker
- [ ] Empty and sparse-data states — a new user with three days of logs should see something useful, not a broken axis

### 3.3 Settings and customization

- [ ] Settings page shell with sections for profile, symptoms, habits, medications, export, and account
- [ ] Edit profile — display name and a searchable timezone picker
- [ ] Manage symptoms — list system and custom rows together, add a custom symptom, hide/show any row, delete custom rows
- [ ] Manage habits — same as symptoms, plus `tracking_type` and `unit` when adding a custom habit
- [ ] Manage medications — add, edit, and remove, with name, dosage, and frequency
- [ ] Delete account — typed confirmation, explicit warning that all data is removed permanently, then `DELETE /api/users/me` and redirect to a logged-out screen

### 3.4 Export

- [ ] `GET /api/export/csv?startDate=&endDate=` — stream a CSV covering all log types in the range; stream rather than buffering so a heavy user does not blow up memory
- [ ] Decide and document the CSV shape (one row per log entry with a `type` column is simplest for spreadsheet use)
- [ ] Format timestamps in the export using the user's timezone and include the zone in the header row
- [ ] Settings action that requests the export with a date range and triggers the browser download
